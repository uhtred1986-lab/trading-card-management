# #566 unknown-provider-outcome audit (read-only, 2026-10-12)

This is a design audit against current main `23da6829`, not a recovery implementation or a claim that #566 acceptance is complete. The first checkbox in `pv-s02.md` remains open. No live database or paid provider was used.

## Observed behavior

`act()` persists the human action and returns before `advanceGame()` is launched by ArenaStage. `advance()` claims a row keyed by `(gameId, revision)` and marks it `attempting` before sending a provider request. A competing advance is busy. If an `ai_runs` result and its selected semantic Action were saved, the stable call ID permits replay, one usage receipt, one decision row, and one revision-CAS application. The PGlite proof in `scripts/verify/arena-advance-leases.mts` exercises those cases with a fake provider, including a blocked request and a reordered legal menu.

If the provider request may have completed but no result was durably saved, `claimAdvance()` changes an expired `attempting` row to `attention`; later calls return `attention` and never resend it. `advance()` returns an unknown-outcome error. ArenaStage renders Retry, but Retry only calls `advanceGame()` again, so this particular state cannot resume the match. The browser preview proof checks the retry interaction with a mocked advance action; it does not prove recovery of this backend state.

The reason for the fence is real: the provider has no demonstrated idempotency/retrieval contract. A lost response cannot be reconstructed from a lease. Retrying the paid request could duplicate the call and its charge. Automatically *continuing the game with a different decision* is possible, but it is not recovery of the original provider answer.

## Bounded no-provider continuation candidate

After the attempt lease expires, have a server request load the authoritative game and inspect the private lease and `ai_runs` for the original call ID. Prefer the recorded result if it exists and still matches the legal menu. If the row remains `attention` with no recorded result, acquire a distinct, fenced recovery owner for that exact `(gameId, revision)` with a conditional update; do not reenter `chooseMove()` or `ruleOnCard()`. The recovery path must recheck the game revision, prompt, and lease phase before selecting and applying anything. Stale clients and concurrent recovery requests must be harmless.

For an AI move, choose a deterministic Action from the current server-owned legal list (for example, the first legal entry, matching the existing no-API-key behavior), save the **semantic Action**, and record `decidedBy: "fallback"` with an explicit “provider outcome unknown; continued without another request” explanation. Apply it through `applyToGame()` and its revision CAS, then mark the recovery complete. Persist enough private recovery state before application to survive a worker crash and replay only that same Action. Do not treat the missing provider response as zero-cost evidence, fabricate an `ai_runs` row, or create an `arena_ai_usage` receipt with unknown usage. The original paid call might have charged externally; its cost is unknown until a real result or provider record arrives. A late original worker must fail its owner/phase fence and must never overwrite or apply the fallback. If its genuine `ai_runs` result arrives later, any accounting reconciliation must use the original call ID once and must not replace the applied gameplay decision.

An unrecorded **referee** outcome is different. `refereeRuling` accepts an empty program, and `ruleOnCard()` already returns one without an API key, but that skips an unsupported printed effect. A no-provider recovery could apply `ops: []` as an explicitly labelled, invalid one-game ruling; it must not save a draft card rule or imply the effect was interpreted. This is a gameplay policy decision requiring owner review, not a faithful recovery of the unknown paid ruling. If skipping that effect is unacceptable, keep referee `attention` pending an authenticated adjudication path. Thus a move-only fallback would not yet meet #566's general automatic-resume acceptance.

The client should display a public recovery status and offer/trigger the server continuation without receiving the private checkpoint, provider prompt, legal list, or opponent card identities. Current `stateText()` intentionally shows only the AI's own hidden cards and public opponent information; the fallback must not route an AI-private legal menu or debug `promptText` into a player-facing error, Snapshot, narration, or browser request. The current Retry label is misleading for the ambiguous case: a distinct “continue without AI decision” status/action would make the changed gameplay clear. To satisfy *automatic* continuation, a bounded poll or scheduled server worker must invoke recovery after lease expiry; a manual Retry alone is insufficient.

## DB-free verification needed before claiming completion

Use PGlite and a fake provider. Stop one real `advance()` after `markProviderAttempt()` and before `recordRun()`, expire its lease, and race two recovery calls. Assert one deterministic semantic Action, one decision record, one game-revision increment, zero second provider requests, zero fabricated usage receipts, and an explicit fallback origin. Reload before recovery and between checkpoint/application; assert exact-once completion. Release the original provider worker late and assert its response cannot alter the applied move; if its run persists, test one real usage reconciliation by call ID separately. Include a reordered legal menu and changed-revision/stale claimant case. Exercise the referee policy separately, checking no draft rule is written for an invalid no-op and that no private hand/life/deck data appears in client-visible status. Keep the existing recorded-result, contention, and browser retry tests as regression controls.
