No printed card in the repository establishes the generic 8-5-6 wording; this file does not claim one. The rule order comes from DBS manual 8-5-5 through 8-5-10-1 and movement-subject information from 9-6-9-1-3, subject to the 9-6-9-1-2 exceptions.

1. **Replacement of a pre-announced subject.** A Combo card with the legal [Ultimate] route would go to Removed rather than Drop. The 8-5-6 generic Auto matches the announced Combo-to-Drop event, but the projected `leaveRoute` reads [Ultimate] and `vm/battle.ts:348` interrupts under #609 before 8-5-7. The card remains in Combo; no generic effect or physical departure has happened. The current VM never reaches a checkpoint at which it could reconcile that projection with the replacement.
2. **Replacement acquired during 8-5-7.** A generic Auto legally pauses on `chooseCards`; after a JSON reload, choosing the Combo subject installs a mandatory, timed `replaceLeave` to Warp and draws. The effect event precedes the 8-5-8 physical departure. That native departure nevertheless moves the subject to Drop, and the battle-end Auto then resolves. `leaveRoute` in `vm/replace.ts` only discovers standing replacements automatically for an `inPlayZones` departure. Combo is held (`game.zones.combo.host`) but not an `inPlayZones` area, so the installed replacement is ignored. The `battle.ts:380` changed-destination guard consequently never sees it. Choosing no card confirms ordinary order: generic effect, physical departure, battle-end effect. The generic source emits its activation event in the first response before its choice, so it does not activate again after reload.
3. **Optional native replacement question.** Before cleanup, a timed optional Warp replacement is discoverable by `replacementChoices` for the Combo subject, but the native 8-5-8 mover never asks `replaceMove`. The subject goes to Drop and the battle finishes. Thus a successful focused run proves current behavior, not acceptance of the legal 9-10 choice.

The projection path calls `leaveRoute` on a cloned state; its own [Ultimate] hook is read for a held Combo departure, while standing `replaceLeave` checks only `inPlayZones`. The physical native `moved` uses the same gate. This discrepancy explains both a typed interruption for one kind of redirect and a silent bypass for timed replacement redirects. Existing PR #691 proof covered [Ultimate] before projection and simulated a changed 8-5-8 destination by changing the card ID in a saved state. The second scenario here uses a legal Auto choice and persisted replacement effect, without state mutation beyond fixture setup.

The remaining implementation should keep the cleanup progress in the saved `endCombo` record: freeze each pre-announced subject, its current route and projected subject information; resolve 8-5-7; then ask any optional or competing 9-10 choices for each still-present departure and persist the answer/cursor before moving. A replacement that substitutes the departure or redirects it to an area other than Drop must be reconciled with the already-pended generic occurrence and its subject information. No current test or rule citation proves which information to give a pre-announced Auto when its eventual route changes; that boundary remains open and must not be filled by assuming Drop. This is a cleanup-local design, without changing global replacement discovery for unrelated moves.
