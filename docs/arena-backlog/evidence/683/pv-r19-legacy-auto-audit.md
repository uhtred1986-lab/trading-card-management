# #683 legacy Extra Auto continuation (12 Oct 2026)

Rule Manual §§12-2-2/3 and 22-35-2/22-36-2 include successful Extra `[Auto]` skill activations in Heroic/Villainous's second trigger. The word “another” qualifies only the Battle Card play trigger. A `[Field]` Extra with `[Heroic]` and `[Auto] When this card is placed in a Battle Area, draw 1 card.` is a legal, compiler-read route: hand Field activation places it in Battle, then the arrival Auto activates with the source itself in the eligible watcher area. Before this change, the legacy engine emitted Field and Auto skill events and the Auto's draw, but no Heroic draw/spend; a `{r}` price that was paid through native `optionalCost` after JSON reload did the same. Declining the price correctly emitted no Auto skill event or payout.

`engine/engine.ts` now captures matching in-play watcher identities after a free or fully paid Extra Auto begins and before its effect changes the board. The existing checkpoint resolves those keyword Autos after the source effect. The watcher enumerator excludes the source for Battle plays only; it permits an in-play Extra to answer its own Extra skill, including an ordinary Main activation. It does not alter the narrower default `extraActivated` trigger for hand activations. The new standalone `scripts/verify/villainous-683-legacy-auto-audit.ts` asserts legal Field arrival, exact Auto-before-Heroic draw/spend order, no recursion, paid energy-before-skill order and JSON reload, declined and unaffordable nonactivation, own Villainous's opponent choice and indexed spend, and in-play Extra Main self-Heroic. ```

The existing `scripts/verify/villainous-683.ts` focused suite also passes. These are local synthetic proofs. `games.ts` already writes actions, log, beats and mutation receipts in the version-guarded update (`applyToGame`, lines 543–615), with duplicate requests checked before stale revision. A dedicated #683 saved-session proof would stage this legal Field Auto in a local PGlite game, pause at optional cost and later Villainous choice, reload through `loadGame`, apply each action with `expectedRevision` and request identity, compare both viewer snapshots, and prove duplicate and stale requests do not double pay, draw, discard, spend or emit beats. A JSON round trip alone does not prove that persistence behavior. Nested parent continuation order beyond the already-tested parent that ends at invocation, nonhand activation outside the in-play Field route, older grant-only `-1` identity, and catalog prevalence remain separate limits.
