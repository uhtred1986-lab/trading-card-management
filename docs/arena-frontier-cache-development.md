# Resource frontier cache development

This developer-only experiment preserves the resource-aware search scoring model, sampled information boundary and root legal executor. Search stays opt-in; `frontierCache` defaults to false. No difficulty is enabled, and the previous negative 30M holdout remains the strength result. This batch makes no strength claim.

Every search report now carries a bounded decision window, main/offense/defense/other phase, completion or fallback reason and cache counters. Unknown window strings are projected to `other`. Collectors aggregate counts by window and phase, with exact status/reason conservation; there are no action IDs, cards, observations or arbitrary metric keys in this diagnostic projection. The strict portal import manifest remains version1 and carries hashes/outcomes only. Raw evaluator reports/checkpoints remain private local artifacts.

The optional cache exists for one decision only. Its key includes spent resource mask, available energy, excluded resource mask and required resource index; no requirement and a required card outside the resource model are distinct keys. Resource definitions are immutable during that decision. Values contain the full completed subset frontier, retaining its original iteration order. No partial frontier is cached; there is no dominance pruning or score/value memoization. Lookup nodes still poll cancellation/deadline/memory pressure and consume the fixed node budget.

Retention is bounded to64 entries and a64KiB structural reservation, charged within the existing256KiB search reservation. The conservative estimate uses256 bytes for the index,128 per entry and96 per cover; it is not measured JavaScript heap usage. The effective cache capacity shrinks to the remaining search budget. Full/disabled cache insertion falls through to ordinary traversal. Cache overhead can change which searches finish within the same node cap; every incomplete search still returns the exact heuristic answer and RNG. Whenever both cached and uncached searches complete, the full answer and advanced policy RNG must agree. No cache survives the decision, so it cannot retain another player's observations.

Checkpoint format `arena-search-checkpoint-v2` adds mandatory, strictly validated per-game diagnostics. Resume conserves saved rows, status/reason counts, cache sums and maxima without replaying or billing saved attempts. Old v1 checkpoints remain historical receipts and are explicitly refused by this runner instead of inventing missing telemetry. To replay historical v2 experiments, check out their pinned source commit and use its runner, fixture and protocol pins; do not reinterpret an old receipt with this runner. All previously used +10M/+20M/+30M seed ranges are consumed and the development runner refuses reserved sets even with the old `--allow-holdout` flag.

The protocol proposal is machine-readable in `scripts/verify/arena-search-frontier-protocol.ts`: four audited matchups AvA/AvB/BvA/BvB, development indices0–3, both seats,32 games per arm, depth2,3,000-move cap. Compare uncached and cached search against the identical integrated heuristic baseline. The policy seed is7919+2*k+(candidateSeat=p2?1:0); each seat's initial RNG is independently recorded. The fixture deals, budgets and priors are identical between arms. The baseline's separately reviewed last-Life activation fix must be present in both arms. Freeze and review the integrated source before either arm runs. No tuning or holdout run is authorized here.

After integration/source freeze, the two proposed commands are:

```sh
npx tsx scripts/arena-search-eval.mts --seed-set dev --seeds 4 --fixtures AvA,AvB,BvA,BvB --depth 2 --max-moves 3000 --frontier-cache off --checkpoint /tmp/frontier-dev-off-checkpoint.json --out /tmp/frontier-dev-off.json --manifest /tmp/frontier-dev-off-manifest.json
npx tsx scripts/arena-search-eval.mts --seed-set dev --seeds 4 --fixtures AvA,AvB,BvA,BvB --depth 2 --max-moves 3000 --frontier-cache on --checkpoint /tmp/frontier-dev-on-checkpoint.json --out /tmp/frontier-dev-on.json --manifest /tmp/frontier-dev-on-manifest.json
```

A short focused run is explicitly marked `matchesDevelopmentProtocol:false`; even a complete32-game arm is development evidence with `strengthEligible:false`. Report per-window reason distributions, hits/misses/skipped insertions, reservation maxima, completion/fallback rate, move outcomes and latency quantiles. Compare only matching frozen source/fixture/seed/RNG pins, allowing the declared cache flag/policy hash to differ. These small reused development sets can guide engineering; they cannot establish strength or enable a default.

Focused validation covers complete answer/RNG equivalence on120 case/seed pairs, hidden-state twins, JSON reload and input purity; exact budget/host fallbacks; capacity limits; cache configuration hashes; bounded telemetry validation and conservation; and actual evaluator kill/resume with per-game telemetry. Existing tactical and search regression proofs remain required. Browser/Node receipts also include the cache flag and aggregated diagnostics; browser timing remains a separate measured check after source freeze. Unknown rule effects, future extra attacks/counters, resource prior error and tactical skill valuation limitations remain unchanged.

## Frozen development result

No strength promotion follows.
